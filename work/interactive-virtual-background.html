Interactive Virtual Background

A desktop app that replaces and animates a webcam background in real time, then exposes the composited feed to Meet/Zoom/Teams/Slack/Discord as a standard virtual camera device — outside the usual Rails/backend work.

What's actually built

Included deliberately unfinished

What's working: webcam capture with a live preview and FPS readout, a MediaPipe segmentation worker, a Three.js compositor, and a Linux virtual-camera bridge. What's below is the actual system design that drove those decisions, written before most of the code, not after.

Architecture

The real-time frame pipeline

Capture and segmentation run in a Web Worker with OffscreenCanvas — never on the renderer's main thread — so the settings UI stays responsive under segmentation load.

Capture → Segmentation → Compositor → Native Bridge → Virtual Camera → Meet/Zoom/Teams

The hard part

Virtual camera delivery, per OS

The most platform-fragmented part of the whole system. Each OS gets its own genuinely native implementation behind one thin shared interface.

Linuxv4l2loopback kernel module + an ffmpeg pipe — built first, validates the whole pipeline
WindowsMedia Foundation Virtual Camera API — a native, code-signed C++ component
macOSCMIOExtension — its own signed + notarized system-extension target

Design decisions

Tradeoffs, made explicit

Electron over Tauri

macOS's WKWebView has historically had rougher WebGL/OffscreenCanvas/WASM-SIMD parity than Chromium — an unacceptable risk for a 30 FPS ML+GPU pipeline.

MediaPipe over a custom ONNX model

MediaPipe hits the FPS target on mid-range hardware today, with the segmentation backend abstracted behind an interface so a higher-quality model can slot in later without a rewrite.

An adaptive quality controller, not a scheduler

A hysteresis state machine watches actual frame time and steps a quality ladder up or down — it only ever swaps cheap parameters, never re-initializes the segmentation model.
